# model_effect_calculator

Разделы идут в порядке создания файлов. Семь скриптов от 27 октября 2026 записаны в одну секунду; между ними порядок такой, в каком они легли на диск: `calc.py`, `example.py`, `example_decoding_controls.py`, `example_embeddings.py`, `example_generation.py`, `example_models.py`, `example_temperature.py`. Дальше файлы уже разнесены по времени.

Запуск из корня проекта, интерпретатор — `./venv/bin/python`, если зависимости стоят в виртуальном окружении проекта.

## Пример: бюджет двух моделей

`calc.py` считает, влезет ли модель в бюджет на 10 000 обращений. Один и тот же запрос уже нарезан двумя токенизаторами: GPT видит 78 входных токенов, LLaMA-подобный — 112. Ожидаемый ответ — 500 токенов. Цена GPT — $0.75 / $4.50 за миллион входных и выходных токенов, цена LLaMA — $0.60 и на вход, и на выход. Бюджет — $20.

Функция одна: `estimate_cost` из `utils/cost.py`. Кеш здесь не используется.

```bash
python calc.py
```

Один запрос к GPT стоит $0.0023085, десять тысяч — $23.09. Один запрос к LLaMA стоит $0.0003672, десять тысяч — $3.67. По бюджету проходит только LLaMA.

## Пример: токены и цена текста

`example.py` показывает, что модель читает не символы, а id из словаря токенизатора. Две строки одной длины в символах дают разное число токенов: кириллица, код и эмодзи дробятся сильнее обычного английского. Считать нужно токенизатором той модели, которой уйдёт запрос.

Функции лежат в `utils/tokenization` и `utils/cost.py`.

```bash
python example.py
```

1. GPT через tiktoken. `count_tokens` возвращает число id, `show_tokens` — сами фрагменты. Пробел и запятая тоже токены.
2. TinyLlama через Hugging Face. Скачивается токенизатор, не веса. `▁` отмечает границу слова, `<0xE2>` — байт UTF-8, если готового токена нет. `<s>` добавляет шаблон входа, в исходном тексте его нет. Текст с сердцем после `decode` собирается обратно.
3. Одна пачка строк считается обоими токенизаторами. Столбец `difference` — это `llama_tokens - gpt_tokens`. Плюс значит, что TinyLlama нарезала строку мельче. Это сравнение двух токенизаторов на этих строках.
4. Тот же бюджет, что в `calc.py`: 78 и 112 входных токенов, 500 выходных, 10 000 запросов, потолок $20. GPT выходит на $23.09, LLaMA — на $3.67.
5. Длинный промпт: 12 000 входных и 1 500 выходных токенов по ценам $0.75 и $4.50. Без кеша один запрос стоит $0.01575, десять тысяч в день — $157.5. Если 8 000 токенов повторяющегося начала идут по $0.075 за миллион, запрос стоит $0.01035, день — $103.5.
6. BERT добавляет `[CLS]` и `[SEP]`. Префикс `##` — пометка WordPiece, что фрагмент продолжает слово, к служебным токенам он не относится.

| `count_hf_tokens`, `show_hf_tokens`, `get_hf_tokenizer` | То же для TinyLlama, со служебным токеном и без |
| `show_bert_tokens`, `show_bert_pair_tokens` | Один текст и пара предложений в BERT |

## Пример: top-k, top-p и штрафы за повтор

`example_decoding_controls.py` разбирает, что происходит с логитами между forward pass и выбором токена. Сами операции лежат в `utils/models/decoding.py`, сценарии урока — в `utils/models/decoding_lesson.py`. Этот файл только вызывает их по порядку.

```bash
python example_decoding_controls.py
```

Порядок обработки фиксирован:

```
логиты → repetition_penalty или frequency_penalty → temperature → top-k → top-p → greedy или sampling
```

Температура меняет остроту и никого не выбрасывает. top-k оставляет фиксированное число лучших. top-p оставляет минимальный набор, чья суммарная вероятность не меньше порога. `repetition_penalty` один раз снижает логит уже встреченного id. `frequency_penalty` вычитает штраф за каждое предыдущее появление.

Сценарии идут так: top-k, top-p, температура, плоская шапка распределения, какой параметр лечит какой симптом, оба штрафа, симптомы повтора, сборка конвейера, учебные случаи, затем gpt2. Модель английская, промпт тоже английский. Генерация жадная: `do_sample=False`, поэтому top-k и top-p на этом прогоне не участвуют, а `repetition_penalty` логиты всё равно меняет. Ответ ограничен 35 новыми токенами. При первом запуске веса gpt2 скачиваются.

| Функция | Зачем |
| --- | --- |
| `apply_temperature`, `apply_top_k`, `apply_top_p` | Острота распределения и два фильтра кандидатов |
| `apply_repetition_penalty`, `apply_frequency_penalty` | Штраф за факт повтора и за число повторов |
| `demo_top_k` … `demo_cases` | Таблицы урока на заданных логитах |
| `demo_gpt2` | Жадный прогон gpt2 при нескольких значениях штрафа |
| `generate_greedy_text` | Один жадный ответ с заданным штрафом |

## Пример: таблица входных эмбеддингов

`example_embeddings.py` показывает, что token id — это номер строки в таблице эмбеддингов. Строка — вектор фиксированной длины. Отдельное число в нём не переводится «на русский»: модель использует вектор целиком.

Входной эмбеддинг ещё не знает предложение. Один и тот же id всегда достаёт одну и ту же строку, даже если слово в двух фразах значит разное. «Замок» на холме и «замок» на двери совпадают. Различать значения модель начинает в слоях трансформера.

Модель — `cointegrated/rubert-tiny2`. Таблица имеет форму `[83828, 312]`: 83 828 строк словаря и вектор длины 312. После нормировки на длину 1 скалярное произведение становится косинусным сходством.

Функции лежат в `utils/embeddings`.

```bash
python example_embeddings.py
```

1. Печатает форму таблицы.
2. Слово «замок» — один токен и одна строка. Печатаются id и первые десять чисел вектора.
3. Два предложения про замок на холме и дверной замок. `same_input_embedding` подтверждает, что векторы совпали.
4. Десять ближайших к «замок». Соседи часто оказываются формами слова или словами одной темы, не словарём синонимов.
5. То же для списка кандидатов: улица, город, река, король, музыка, школа, машина, книга. У «улица» ближайшие на этой модели обычно формы слова (улицы, улиц, улице, улицами) и городская тема (дорога, шоссе, бульвар, переулок). Неочевидный сосед — «река»: не синоним, а похожие географические контексты.

| Функция | Зачем |
| --- | --- |
| `get_embedding_matrix` | Вся таблица входных эмбеддингов |
| `tokenize_without_special`, `get_single_token_id` | Токены слова без `[CLS]` и `[SEP]`, id, если слово целое |
| `get_token_embedding` | Строка таблицы для одного слова |
| `same_input_embedding` | Совпадает ли вектор слова в двух текстах |
| `find_nearest_tokens` | Ближайшие строки по косинусному сходству |

## Пример: один шаг генерации

`example_generation.py` разбирает, что модель не пишет ответ целиком. На каждом шаге она получает текущий контекст, возвращает логиты по всему словарю, softmax превращает их в вероятности, выбирается один токен и дописывается к входу.

```
текст → tokenizer → input_ids → model → логиты последней позиции → softmax → выбор токена
```

Логиты могут быть отрицательными и больше единицы, их сумма ничему не равна. Вероятности лежат от 0 до 1 и в сумме дают 1. Softmax сохраняет порядок, поэтому greedy можно брать и по логитам, и по вероятностям.

Greedy всегда берёт максимум: на одном промпте результат стабилен, но уже выбранные токены могут закрепить повтор. Sampling берёт токен случайно по вероятностям. Готовый `generate(do_sample=True)` по умолчанию ещё режет словарь `top_k=50`; чтобы сравнить с ручным sampling из полного распределения, ставят `top_k=0`.

Длина ответа прямо задаёт latency: 20 новых токенов — около 20 шагов, 200 — около 200. Поэтому API ограничивают `max_new_tokens`.

Модель — `gpt2`. Она обучена в основном на английском, на русских промптах продолжения слабее. Смысл разбора шага от этого не меняется. Функции лежат в `utils/models/generation.py`.

```bash
python example_generation.py
```

1. Пять кандидатов после «Столица Франции —» и ещё трёх коротких промптов.
2. Ручной greedy на «Жил-был», 8 новых токенов, на каждом шаге печатается top-5.
3. Промпт «Это очень очень», 35 токенов: greedy может закрепить повтор.
4. Три жадных запуска того же промпта совпадают. Три sampling-запуска с seed 1, 2 и 3 расходятся.
5. Таблица greedy-следа и sampling из полного распределения с seed 42. `diagnose_generation_checks` отмечает, повторяется ли фраза «я не буду» и отличается ли sampling от greedy.

| Функция | Зачем |
| --- | --- |
| `show_next_token_candidates` | Top-k следующего шага: логит, вероятность, фрагмент |
| `generate_greedy_with_trace` | Жадный цикл с печатью кандидатов |
| `generate_with_strategy` | Greedy или sampling на заданное число токенов |
| `build_greedy_trace` | Таблица шагов без печати по ходу |
| `generate_sample_with_full_distribution` | Sampling без обрезки top-k |
| `diagnose_generation_checks` | Совпал ли greedy сам с собой и ушёл ли sampling в повтор |

## Пример: distilgpt2 и gpt2

`example_models.py` читает архитектуру маленькой causal-модели и сравнивает её с gpt2 по памяти и скорости. Causal-модель предсказывает следующий токен только по левому контексту. distilgpt2 меньше 100 миллионов параметров, её можно разбирать на CPU.

Как читать `print(model)` сверху вниз:

- `wte` превращает token id в вектор. Словарь — 50 257 токенов, длина вектора — 768.
- `wpe` добавляет позицию. Позиций 1024, вектор той же длины.
- `drop` — dropout после сложения двух векторов. В `eval` он выключен.
- `h` — шесть блоков трансформера. Внутри: LayerNorm, attention, остаточное сложение, снова LayerNorm, MLP и ещё одно сложение. Остаточные связи в `print(model)` не видны: это сложение в прямом проходе.
- `c_attn` с выходом 2304 — линейная проекция сразу в Q, K и V: 2304 = 3 × 768.
- `mlp` обрабатывает каждый токен отдельно: 768 → 3072 → 768.
- `lm_head` переводит вектор длины 768 в 50 257 оценок словаря.

Число параметров — ориентир памяти и скорости, не оценка качества. Один параметр в float32 занимает 4 байта, в float16 — 2, в int8 — 1. У distilgpt2 это около 81.91 млн параметров: 312.47 МБ в float32, 156.24 МБ в float16, 78.12 МБ в int8. Активации, KV-cache и фреймворк сюда не входят.

Функции лежат в `utils/models/causal.py`.

```bash
python example_models.py
```

1. Печатает модель и числа конфига: блоки, головы, скрытый размер, словарь, число позиций.
2. Считает параметры и память в текущем dtype, затем оценку для float32, float16 и int8.
3. Жадное продолжение промпта «В этом уроке внимание помогает модели», 30 токенов.
4. Таблица distilgpt2 и gpt2 на 10 и на 30 новых токенах, по три прогона. В колонках — миллионы параметров, память float16, секунды и токены в секунду. gpt2 крупнее, поэтому весит больше и на CPU обычно медленнее. Переход с 10 токенов на 30 увеличивает время: шагов больше. Если память ограничена, берут distilgpt2. По одним параметрам модель не выбирают: важны задача, скорость и ресурсы.

| Функция | Зачем |
| --- | --- |
| `load_causal_model` | Токенизатор и causal-модель, повторный вызов берёт кеш |
| `architecture_summary` | Слои, головы, скрытый размер, словарь, позиции |
| `count_parameters` | Число обучаемых весов |
| `estimate_model_weights_memory_mb` | Память весов в их фактическом dtype |
| `estimate_memory_mb` | Та же оценка при заданном числе байт на параметр |
| `generate_continuation` | Короткое жадное продолжение |
| `measure_generation_speed` | Среднее время и токены в секунду по нескольким прогонам |

## Пример: температура

`example_temperature.py` показывает, что температура делит логиты перед softmax и не меняет порядок кандидатов. Самый вероятный токен остаётся самым вероятным. Меняется острота.

Низкая температура делает распределение острым: текст стабильнее и формат строже, сюжет чаще шаблонный. Высокая выравнивает распределение: появляются необычные детали, связность и точность инструкции страдают чаще. Значение 0 в этом примере означает greedy, `do_sample=False`. В `generate` ноль не передаётся: без sampling температура случайностью не управляет.

`generate_text` возвращает только продолжение после промпта. Модель — `roneneldan/TinyStories-Instruct-33M`, её можно гонять на CPU. Промпт про робота и сад написан по-русски, хотя модель училась на английских сказках: продолжения слабее, чем в уроке, разница температур видна. Seed 42 фиксирует sampling. Ответ — 120 новых токенов.

```bash
python example_temperature.py
```

Три прогона одного промпта:

| Температура | Что ожидать |
| ---: | --- |
| 0 | Greedy: связный и простой текст |
| 0.7 | Спокойный sampling, конкретные детали, иногда лишний формат вроде «Краткое содержание» |
| 1.5 | Больше образности и риск странных переходов |

| Функция | Зачем |
| --- | --- |
| `load_causal_model` | TinyStories и её токенизатор |
| `generate_text` | Продолжение при температуре 0, 0.7 или 1.5 |

## Пример: OpenRouter

`example_openrouter.py` отправляет Chat Completions не в OpenAI, а на `https://openrouter.ai/api/v1`. Ключ берётся из `OPENROUTER_API_KEY` или из локального `.env` и в вывод не попадает. Клиент ждёт один запрос до 90 секунд: бесплатные модели отвечают медленно. В тексте урока для иллюстрации указано 30.

Функции лежат в `utils/openrouter`.

```bash

```

2. Пауза между повторами растёт от попытки к попытке. Повторяются 429, тайм-аут, обрыв связи и 5xx. Ошибки запроса и доступа не повторяются.

4. Каталог сообщает, поддерживает ли выбранная модель `temperature`, `max_tokens` и `seed`.
5. Две бесплатные модели разных разработчиков получают одни и те же три промпта. Сравниваются текст, число токенов и учебная стоимость: $1 и $4 за миллион входных и выходных токенов. Это не прайс выбранной модели.

## Пример: seed, JSON и надёжность

`example_json_reliability.py` показывает, как принимать ответ модели в сервис, а не только как его сгенерировать. Сначала всё проверяется на заготовленных строках, без API. Потом два запроса с `seed=42` и восемь обращений в техподдержку через бесплатную модель OpenRouter.

Функции лежат в `utils/openrouter`.

```bash
python example_json_reliability.py
```

1. Корректный JSON ещё не значит, что ответ можно использовать. JSON mode требует синтаксис и не проверяет имена полей. `parse_and_validate` отвергает не-JSON и ответ без обязательных полей.
2. Тот же контракт описан схемой и моделью Pydantic `SupportRequest`: категория, приоритет и короткое резюме из заранее известного набора.
3. Корректирующий повтор показывает модели её предыдущий текст и причину отказа. Это не технический retry и не fallback. Локальный прогон проходит три ответа: два плохих и один годный.
4. Из 20 обращений 14 проходят сразу, 4 — со второй попытки, 1 — с третьей, 1 остаётся неуспешным. Накопительный success rate после попыток: 0.70, 0.90, 0.95. Повторы исправляют 5 обращений, одно уходит в fallback и в долю успеха не входит.
5. Один и тот же запрос дважды уходит с `seed=42`. Совпадение текстов уменьшает разброс и его не гарантирует.
6. Восемь тестовых обращений идут через JSON mode. Считается тот же success rate уже по живым ответам.

## Пример: длинный контекст

`example_long_context.py` показывает, почему длинный вход дорожает быстрее, чем растёт. Внимание строит матрицу «токен на токен». Удвоение длины увеличивает матрицу в четыре раза, вместе с ней растут память и время prefill. TTFT — время до первого токена — и есть этот prefill. Сам ответ идёт уже токен за токеном.

## Пример: static и continuous batching

`example_batching.py` показывает, почему схема «один запрос — один проход модели» плохо загружает GPU и чем continuous batching отличается от static. Модель и видеокарта не нужны: запрос задаётся только числом шагов генерации. Один шаг — один токен ответа.

Функции лежат в `utils/inference/batching.py`. Симулятор меняет объекты запросов, поэтому каждая очередь создаётся заново перед прогоном.

Запуск из корня проекта:

```bash
python example_batching.py
```

### Что сравнивается

**Latency** — время от отправки одного запроса до ответа. Его замечает пользователь.

**Throughput** — сколько запросов система успевает обработать за единицу времени. Он важен, когда запросов становится много.

Пока запросы идут по одному, latency низкий, но GPU занят слабо: при батче размера 1 матрицы узкие, и тысячи ядер простаивают. Загрузка около 30% в таком режиме ожидаема. Это не поломка карты и не следствие маленькой модели или параметра `temperature`. Батч занимает GPU плотнее и поднимает throughput, но каждый запрос начинает ждать соседей, поэтому latency растёт.

**Static batching** собирает пачку один раз и держит её, пока не закончится самый длинный ответ. Короткий запрос после конца генерации остаётся в слоте и больше не делает полезной работы.

**Continuous batching** освобождает слот сразу и ставит в него следующий запрос из очереди. Состав батча может меняться на каждом шаге. Этот приём лежит в основе vLLM, TGI и TensorRT-LLM. Выигрыш есть не всегда: очередь должна быть длиннее батча, а длинные запросы должны приходить вперемешку с короткими. Если после текущего батча очередь пуста или все длинные запросы стоят отдельной пачкой, continuous отрабатывает так же, как static.

### Шаги примера

1. Объясняет, почему одиночный инференс оставляет GPU полупустым и почему latency с throughput конфликтуют.
2. Считает потери static batching на восьми запросах в одном батче: семь ответов по 50 токенов и один на 2000. Полезная работа — 2350 слото-шагов, всего их 16 000, впустую уходит 13 650, то есть 85%.
3. Прогоняет 12 запросов длиной `[3, 8, 2, 5, 4, 3, 6, 2, 5, 4, 3, 7]` при батче из 4 слотов. Печатает таблицу «слот × шаг»: буква — идентификатор запроса, точка — простой.
4. Сравнивает две очереди из 8 запросов с одинаковой суммой работы, 800 шагов. Однородная — все по 100. Скошенная — семь по 25 и один на 625. Все запросы сразу входят в батч, подставлять в освободившийся слот некого.
5. Повторяет сравнение на 32 запросах. В скошенной очереди сначала идут 28 коротких, затем 4 длинных. Слоты освобождаются одновременно и снова забирают одинаковых соседей.
6. Перемешивает нагрузку: 4 длинных запроса равномерно стоят среди 28 коротких. Длинный запрос остаётся в своём слоте, а через остальные идёт поток коротких.

### Ожидаемые числа

На двенадцати запросах:

| Стратегия | Шаги | Полезные слоты | Все слото-шаги | Утилизация |
| --- | ---: | ---: | ---: | ---: |
| Static | 21 | 52 | 84 | 61.9% |
| Continuous | 18 | 52 | 72 | 72.2% |

В static короткий запрос C заканчивается через два шага, и его слот пустует до конца батча. В continuous на это место сразу встаёт E. Точки остаются только в хвосте, когда очередь уже пуста.

Дальше отношение числа шагов static к continuous:

| Очередь | Static | Continuous | Выигрыш |
| --- | ---: | ---: | ---: |
| 8 одинаковых по 100 | 100 шагов, 100% | 100 шагов, 100% | 1.00x |
| 8 скошенных, все в одном батче | 625 шагов, 16.0% | 625 шагов, 16.0% | 1.00x |
| 32 одинаковых | 400 шагов, 100% | 400 шагов, 100% | 1.00x |
| 32 скошенных пачкой: короткие, потом длинные | 700 шагов, 57.1% | 700 шагов, 57.1% | 1.00x |
| 32 скошенных вперемешку | 2500 шагов, 16.0% | 700 шагов, 57.1% | 3.57x |

Утилизация continuous на перемешанной очереди не равна 100%. Когда очередь кончается, освободившиеся слоты уже нечем занять, и простой в хвосте остаётся. Выигрыш 3.57x набран раньше, пока в очереди ещё было кого подставить.

## Пример: KV-cache

`example_kv_cache.py` показывает, почему авторегрессивная генерация без кеша пересчитывает одни и те же ключи и значения, сколько памяти за это платит KV-cache и как prefix caching переиспользует общий префикс между запросами. В конце скрипт замеряет жадную генерацию с `use_cache=True` и `use_cache=False`.

Функции лежат в `utils/inference/kv_cache.py`. Формулы памяти и prefix caching считаются без модели. Замер грузит модель.

Запуск из корня проекта:

```bash
python example_kv_cache.py
```

### Зачем кеш

Модель выдаёт ответ по одному токену. Наивный шаг каждый раз прогоняет всю уже известную последовательность: промпт и то, что уже сгенерировано. K и V токена на своей позиции при этом не меняются. Если промпт длиной P, а ответ длиной L, длины шагов — P, P + 1, …, P + L − 1. Сумма этих длин порядка (P + L)².

KV-cache сохраняет K и V после первого прохода. Prefill читает промпт один раз, дальше каждый новый токен добавляет в проход только себя. Работа становится линейной: P + L − 1 токенов. В `transformers` за это отвечает `use_cache`, по умолчанию он включён.

На промпте авторского замера, 801 токен и 100 токенов ответа, без кеша через модель проходит 85 050 токенов, с кешем — 900. Отношение 94.5x. Это верхняя оценка повторной работы, а не обещание такого же отношения секунд: шаг без кеша считает широкую матрицу и лучше занимает GPU, поэтому один токен там дешевле. Секунд всё равно больше, потому что токенов гораздо больше.

Короткий промпт «Привет, как» (3 токена, 3 шага) даёт скромные 12 против 5 токенов. На коротком тексте кеш почти не заметен.

Память после первого шага прыгает вверх, затем растёт линейно. Скачок — это K и V всего промпта на prefill. Дальше каждый шаг дописывает одну пару. Веса загружаются один раз при старте и в этот рост не входят. Очищать кеш после каждого токена нельзя: модель снова начнёт пересчитывать всю последовательность.

### Сколько весит кеш

Размер в байтах:

`2 × слои × KV-головы × d_head × seq_len × batch × байт на число`

Двойка — отдельные тензоры K и V. `seq_len` растёт во время генерации. `batch` умножает кеш, потому что у каждого запроса он свой. Для float16 последнее число равно 2. В уроке 1 МБ = 1024 × 1024 байт.

Модель задания без GQA: 32 слоя, 32 KV-головы, `d_head` 128, 4096 токенов, batch 1. Кеш одного запроса — 2048 МБ, то есть 2 ГБ. Восемь таких запросов — 16 384 МБ, 16 ГБ только под кеш. Один токен этой модели весит 0.5 МБ, поэтому prefill на 10 000 токенов занимает 5000 МБ, и дальше память прибавляет по 0.5 МБ за токен.

GQA делит одни K и V между несколькими головами запроса, и в формуле остаётся `num_kv_heads`, а не полное число голов. У Qwen2.5-3B 16 голов запроса и 2 группы K/V: кеш меньше в 8 раз. У локальной Qwen2.5-0.5B-Instruct 24 слоя, 14 голов запроса, 2 KV-головы и `d_head` 64, то есть кеш меньше в 7 раз. На промпт в 801 токен и 100 новых токенов он занимает 10.6 МБ.

### Prefix caching

Обычный KV-cache живёт внутри одной генерации. Prefix caching оставляет K и V неизменного начала для следующих запросов. Экономия тем больше, чем длиннее общий префикс, чем короче уникальный хвост и чем чаще этот префикс встречается. Если общего начала нет, сохранять нечего.

FAQ-бот: база знаний 2000 токенов, вопрос 20, 100 запросов.

| Режим | Токены prefill |
| --- | ---: |
| Каждый запрос читает префикс заново | 202 000 |
| Префикс считается один раз | 4 000 |

Объём меньше примерно в 50 раз: `2000 + 100 × 20 = 4000` против `100 × 2020 = 202000`.

Второй бот: префикс 5000, вопрос 50, 200 запросов. С prefix caching prefill обрабатывает 15 000 токенов (`5000 + 200 × 50`). Без него было бы 1 010 000, примерно в 67 раз больше.

### Замер

Урок грузит `Qwen/Qwen2.5-3B-Instruct` во float16 на CUDA. Промпт — фраза «Расскажи подробно про историю развития языков программирования. », повторённая 50 раз. Перед сравнением идёт прогрев на 5 токенах: первый вызов медленнее из-за разовой подготовки ядер. Дальше 100 жадных токенов с кешем и 100 без. `do_sample=False` нужен потому, что у Qwen2.5-Instruct в generation config включено сэмплирование, и без этого флага траектории разойдутся. На CUDA и MPS таймер ждёт `synchronize` до и после `generate`, иначе измеряется постановка задачи в очередь. `min_new_tokens` равен `max_new_tokens`, чтобы конец последовательности не оборвал один из прогонов раньше.

На этой машине нет CUDA, модель урока около 6 ГБ не скачивается. Та же схема идёт на уже лежащей в кеше `Qwen/Qwen2.5-0.5B-Instruct` и на MPS, float16. Токенизатор семейства Qwen2.5 даёт ту же длину промпта, 801 токен.

| Прогон | С кешем | Без кеша | Ускорение |
| --- | ---: | ---: | ---: |
| GPU урока, Qwen2.5-3B | 5.20 с | 43.74 с | 8.4x |

## Пример: flash-attention и квантизация

`example_flash_quantization.py` разбирает два способа уместить модель в память GPU. Flash-attention не меняет результат внимания: он перестаёт записывать матрицу seq × seq в медленную HBM и считает её блоками в SRAM. Квантизация уменьшает сами веса. INT8 и INT4 экономят память ценой округления. GPTQ и AWQ подбирают это округление по калибровочным текстам.

Функции лежат в `utils/inference/flash_quant.py`.

Запуск из корня проекта:

```bash
python example_flash_quantization.py
```

### Flash-attention

HBM — большая память видеокарты, где лежат веса и KV-cache. SRAM — быстрая память на чипе, её единицы или десятки мегабайт. Ядра считают только то, что уже в SRAM. Обычный attention для 8000 токенов строит матрицу из 64 миллионов чисел, во float16 это 122 МиБ. В SRAM условных 20 МиБ она не входит, поэтому несколько раз ездит в HBM. Шаг упирается в память, а не в арифметику.

Одна матрица, без голов и без батча:

| Длина | Матрица, МиБ | Влезает в 20 МиБ |
| ---: | ---: | --- |
| 128 | 0.03 | да |
| 1024 | 2.00 | да |
| 4096 | 32.00 | нет |
| 8192 | 128.00 | нет |

На коротком запросе возить почти нечего. С нескольких тысяч токенов выигрыш становится заметным. В transformers быстрые ядра включаются параметром `attn_implementation="flash_attention_2"`. Пакет `flash-attn` собран под NVIDIA. На этом Mac CUDA нет, поэтому пример считает размеры матрицы и не загружает ядра.

### Память весов

Формула считает только сами числа, без масштабов блоков. 1 ГиБ здесь — это 1024³ байт. Урок округляет тот же ряд до 5.8 / 2.9 / 1.4 ГБ.

| Формат | Биты | 3 миллиарда параметров |
| --- | ---: | ---: |
| float16 | 16 | 5.59 ГиБ |
| INT8 | 8 | 2.79 ГиБ |
| INT4 | 4 | 1.40 ГиБ |

70 миллиардов параметров во float16 — 140 ГБ, если гигабайт считать как 10⁹ байт. В одну карту это не помещается.

Равномерный INT4 на отрезке от −0.4 до 0.4 даёт 16 ступеней и шаг 0.053. Вес 0.0231 встаёт на ступень 8 и разворачивается в 0.0267. NF4 ставит те же 16 уровней гуще около нуля: следующий положительный уровень после нуля — 0.0796, а равномерный шаг на отрезке [−1, 1] равен 0.1333. В конфиге урока это `bnb_4bit_quant_type="nf4"` и `bnb_4bit_use_double_quant=True`: свой масштаб на блок из 64 весов, и эти масштабы тоже квантуются.

На GPU урока `Qwen2.5-3B-Instruct` занял 5.75 ГБ во float16 и 1.93 ГБ в INT4, то есть в 3.0 раза меньше, не в 4. Эмбеддинги и масштабы остаются шире четырёх бит. По скорости INT4 там медленнее: 18.20 с и 19.6 ток/с против 13.10 с и 25.5 ток/с. Запросы короткие и идут по одному, а перед каждым умножением веса разворачиваются обратно во float16. Квантизация в этом режиме — инструмент памяти. Ускорение на длинных батчах бывает, но заранее его не обещают.

### Какой метод брать

Качество после INT4 может просесть, особенно на многошаговой математике. Это проверяют бенчмарком. Сжатие само по себе ответы не улучшает и генерацию не ломает.

| Сценарий | Метод |
| --- | --- |
| Длинный контекст, узкое место — скорость attention | Flash-attention |
| Десятки тысяч токенов, attention упирается в память и время | Flash-attention |
| Нужно примерно вдвое ужать веса и остаться рядом с FP16 | INT8 |
| Памяти не хватает немного, качество сложных ответов трогать не хочется | INT8 |
| Модель не влезает, качество можно снизить | INT4 |
| Крупная модель, нужно меньше GPU, небольшая потеря качества допустима | INT4 |
| Нужна посттренировочная INT4 и есть калибровочный набор | GPTQ или AWQ |
| Нужна INT4 с меньшей потерей качества по статистике калибровки | GPTQ или AWQ |

GPTQ компенсирует ошибку одних весов правкой других внутри слоя. AWQ по активациям защищает небольшую долю важных весов. Оба метода применяют к уже обученной модели.

Эталон задачи про ноутбук: 80 000 × 1.15 = 92 000, × 0.75 = 69 000, × 0.90 = 62 100.

### Локальный замер

Bitsandbytes и flash-attn здесь не запускаются. Пример берёт уже скачанную `Qwen/Qwen2.5-0.5B-Instruct` на MPS. Сначала модель отвечает во float16. Потом 169 матриц Linear, 493 961 216 параметров, округляются блоками NF4, и восстановленные числа записываются обратно во float16. Второй прогон видит ошибку округления. Упакованных четырёхбитных весов в генерации нет, поэтому память процесса не падает.

Оценка хранения: сейчас 0.92 ГиБ, почти всё это Linear. В NF4 с double quant те же матрицы заняли бы 0.24 ГиБ, модель меньше в 3.88 раза. Это ближе к четырём, чем 3.0x у 3B на GPU: у 0.5B доля эмбеддингов и норм в общем объёме мала, остаток сверх чистых 4 бит — масштабы блоков.

Потолок ответа локально 512 токенов. У 0.5B объяснение длиннее, чем у 3B, и потолок урока в 256 обрезает цепочку процентов на последней скидке.

| Прогон | Память | Время | Токены | Ток/с |
| --- | ---: | ---: | ---: | ---: |
| float16, MPS | 0.92 ГиБ | 27.92 с | 506 | 18.1 |
| после округления NF4 | 0.92 ГиБ | 10.92 с | 321 | 29.4 |

Вторая строка памяти — та же float16-модель. 29.4 ток/с против 18.1 — это прогрев MPS на первом длинном прогоне, не ускорение от квантизации. Оба прогона умножают float-веса.

Ответы этого запуска:

- Столица Франции в обеих версиях — 巴黎, то есть Париж.
- Перевод «собака» есть в обеих. После NF4 фраза стала длиннее: не «Dog.», а целое предложение со словом dog.
- Float16 дошёл до 92 000 и 69 000, а скидку 10% прибавил вместо вычитания и назвал 75 900. NF4 цепочку сломал: сложил 15% дважды и закончил на 22 600. Итога 62 100 нет ни там, ни там. Дополнительный развал после NF4 — цена округления, промах float16 — ещё и слабость модели 0.5B.
- Предложение о сне осталось связным во float16. После NF4 в нём появились лишние детали вроде «генетических характеристик» и пользы сна для зрения.

Повторный запуск сдвинет секунды. Картина памяти и то, на каком вопросе округление портит ответ, остаются теми же.

## Пример: vLLM и поток запросов

`example_vllm.py` показывает, чем сервер инференса отличается от `transformers.pipeline`, как PagedAttention режет KV-cache на страницы и при какой пачке одновременных запросов pipeline упирается в потолок. Функции лежат в `utils/inference/vllm_serving.py`.

Запуск из корня проекта:

```bash
python example_vllm.py
```

График этого прогона: `outputs/vllm_throughput.png`.

### Зачем сервер

Pipeline удобен для одного запроса и прототипа. Он не делает continuous batching: следующий запрос ждёт, пока закончится текущий вызов. vLLM принимает запросы по HTTP, складывает их в общий батч и отдаёт ответы по мере готовности. Это отдельный движок, а не pipeline внутри HTTP-обёртки.

PagedAttention хранит KV-cache страницами, по той же идее, что виртуальная память ОС. Сплошная схема заранее бронирует на запрос непрерывный кусок под максимальную длину. Короткий ответ оставляет в нём пустоту, и отдать её соседу нельзя. Страницы выдаются по мере роста ответа и возвращаются в пул, когда запрос закончился. Меньше фрагментации — больше одновременных кешей на той же карте и плотнее батч. Число FLOP на токен от этого не растёт, и одиночный запрос в несколько раз сам по себе не ускоряется.

Учебные четыре ответа длиной 20, 50, 10 и 100 токенов. Полезный кеш — 180 токенов.

| Схема | Забронировано | Пусто |
| --- | ---: | ---: |
| Сплошной кусок по 128 токенов | 512 | 332 (65%) |
| Страницы по 16 | 224 | 44 (20%) |

Пустота страниц — только незаполненный хвост последней страницы.

### Когда переходить

На одном запросе за раз объединять некого, pipeline и vLLM близки. Дальше pipeline складывает время в цепочку, throughput стоит на месте. vLLM растит throughput, пока одиночный проход недогружал карту.

На GPU урока 16 одинаковых запросов к vLLM:

| Concurrency | Время | Throughput | Ожидание пользователя | Обслуживание |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 58.3 с | 0.27 запр/с | 30.60 с | 3.58 с |
| 4 | 10.8 с | 1.48 запр/с | 6.30 с | 2.65 с |
| 16 | 3.2 с | 5.07 запр/с | 3.07 с | 3.07 с |

При одном слоте запросы отправили разом, поэтому человек ждёт очередь, а сервер на сам ответ тратит около 3.5 с. При шестнадцати слотах очереди нет, и две метрики сходятся. Для чата с пиком 20–30 одновременных запросов урок советует перейти на vLLM. Вторая копия pipeline на той же карте память только делит и батч не собирает.

Учебный замер — throughput и средние задержки. В продакшне к ним добавляют время до первого токена, время на один токен и хвосты p95/p99.

### Запуск сервера

```bash
vllm serve Qwen/Qwen2.5-3B-Instruct --max-model-len 2048 --gpu-memory-utilization 0.85 --dtype half --port 8000 --enforce-eager
```

| Флаг | Что задаёт |
| --- | --- |
| `--max-model-len` | Промпт плюс ответ, в токенах. При нехватке памяти окно укорачивают, учебному тесту хватает 2048 |
| `--gpu-memory-utilization` | Доля VRAM под веса, активации и KV-cache. 0.85 оставляет запас; vLLM забирает её при старте, поэтому pipeline рядом не держат |
| `--tensor-parallel-size` | На сколько GPU разрезать веса. Четыре карты — это значение 4 |
| `--dtype half` | Float16. Карта T4 не умеет bfloat16, который vLLM выбрал бы сам |
| `--enforce-eager` | Без компиляции CUDA-графов: быстрее старт, чуть медленнее инференс |

`--enable-prefix-caching` в бенчмарк не входит. Все 16 запросов одинаковые, и общий префикс дал бы vLLM фору перед pipeline. Для FAQ-бота с длинным system-промптом этот флаг как раз включают.

Клиент — OpenAI SDK с `base_url=http://localhost:8000/v1` и любой непустой `api_key`. `temperature=0` совпадает с жадным `do_sample=False` у pipeline. Готовность сервера — ответ 200 от `/v1/models`. Нагрузочный тест шлёт 16 запросов через `AsyncOpenAI` и семафор: concurrency 1, 4 и 16. Время пользователя считается от создания задачи, время обслуживания — только пока запрос был внутри семафора.

На этой машине нет ни исполняемого `vllm`, ни CUDA. Процесс не запускается, `http://localhost:8000/v1/models` молчит. Если сервер уже поднят, пример сам прогонит живой клиент.

### Локальный замер

Вместо сервера пример грузит `Qwen/Qwen2.5-0.5B-Instruct` на MPS. Промпт урока проходит через chat template. Прогрев — один ответ на 80 токенов, в таблицу не входит. Затем 16 запросов по одному и две статические волны: 4 и 16 одинаковых промптов. Для равной длины такая волна близка к пачке, которую continuous batching забрал бы разом, но состав батча по ходу генерации не меняется.

Pipeline по одному: 16 запросов за 47.2 с, 0.34 запр/с, обслуживание 2.95 с.

Те же 16 запросов, отправленные разом, волны по измеренному времени батча:

| Concurrency | Время | Throughput | Ожидание | Обслуживание |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 47.2 с | 0.34 запр/с | 25.08 с | 2.95 с |
| 4 | 42.4 с | 0.38 запр/с | 26.49 с | 10.60 с |
| 16 | 7.1 с | 2.26 запр/с | 7.08 с | 7.08 с |

При одном слоте снова видна очередь: человек ждёт 25 с, сервер работает 2.95 с. Волна из 4 на этом Mac почти не быстрее четырёх отдельных ответов, throughput 0.38 против потолка 0.34. Волна из 16 заканчивается за 7.1 с, это 2.26 запр/с и примерно 6.6x к потолку. На GPU урока отрыв сильнее и начинается раньше: там одиночный проход оставляет карту ещё более пустой, а движок vLLM ещё и меняет состав батча на каждом токене. Повторный запуск сдвинет секунды.
